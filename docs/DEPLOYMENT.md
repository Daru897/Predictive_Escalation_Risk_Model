# Setup and deployment

## Local setup

Use Node 24. From `web/`, run `npm ci`, `npm run build`, `npm start`. The app listens on http://127.0.0.1:3001. Both server and worker use the same absolute SQLite path. The start script loads `.env.local`, then `.env` without exposing secrets.

The public demo works without credentials. For private workspaces, copy `.env.example` to `.env.local`, choose a high-entropy `SETUP_KEY`, and generate `TOKEN_ENCRYPTION_KEY` with `openssl rand -hex 32`. Restart, create a private workspace using the setup key, and save the one-time owner access key in your password manager. `SETUP_KEY` permits workspace creation; it does not open existing workspaces.

Owner keys permit imports, interventions, connector configuration and viewer creation. Viewer keys permit reads and exports. Keys are SHA-256 hashed in storage; session cookies are HttpOnly and SameSite=Lax and expire after seven days. Viewer revocation deletes both keys and active viewer sessions. No account recovery email, individual attribution, owner key rotation or SSO is implemented. Losing the owner key requires administrator recovery from a backup or a future recovery tool. Do not publish or send keys in URLs.

## Docker / Compose

From repository root: `docker compose up --build`. Open http://localhost:3001 (the configured origin). Set SETUP_KEY and TOKEN_ENCRYPTION_KEY in the shell or Compose's root `.env` before starting for private mode. The named disk keeps data across restarts. Docker itself was not available in the development environment; local standalone execution is tested, container execution still needs verification.

## Render

The root `render.yaml` defines a paid Starter Docker service with a 1 GB persistent disk and **one instance**. Import the blueprint using the desired branch. Review the paid resources before creating them. No cloud resources were created as part of this rebuild.

Set `APP_ORIGIN` to the exact public HTTPS origin, without a trailing slash. Set `TOKEN_ENCRYPTION_KEY` to a stable 64-character hex secret. `SETUP_KEY` is generated by the blueprint; keep it private and retrieve it in your hosting dashboard for workspace onboarding. Secure cookies are enabled. Confirm the mounted `/app/data` directory is writable by the image's `node` user; the host mount may override build-time ownership.

`npm start` (the container uses the same start script) supervises both processes. Web or worker exit stops the other process. Worker heartbeat is visible in the workspace. `/api/health` checks database access; it does not certify Zendesk connectivity. Use an external health monitor and alert on stale worker/source timestamps before a pilot.

## Storage and operations

The SQLite WAL database supports one host. Do not scale replicas against separate local disks. Application cap: 10,000 tickets/workspace, 500 workspaces, 2,000 rows and 1 MB per CSV. Demo workspaces expire after seven days; private data is retained until explicitly cleared. Each workspace stores at most 100 queue snapshots. These limits are deployment controls, not a load-testing result.

Use SQLite's backup API or a consistent disk snapshot; do not copy only the main database while WAL writes are active. Back up the encryption key separately, test restores, and protect both. Rotation of the encryption key without re-encrypting data makes existing connections unusable; disconnect/reconnect with a controlled migration. Ticket subjects and notes may contain customer information. The connector does not retrieve descriptions, comments, requester emails or attachments, but subjects are not automatically anonymized.

Writes require the configured same origin. The global sign-in/create endpoint is rate-limited and workspace mutations are rate-limited. Edge-level per-client rate limiting, retention policies, SSO, detailed audit logging and incident recovery remain production requirements. The application is a pilot foundation, not a certified enterprise service.

## Dependencies

Production Node dependency audit: zero known advisories at validation. The development-only Next ESLint dependency chain reports five high-severity entries from the `braces` nested-pattern denial-of-service advisory (GHSA-vfj7-8cjw-p6xm). No untrusted glob patterns are accepted by the application. No breaking framework downgrade was applied to suppress the lint-tool advisory. Track upstream remediation.
